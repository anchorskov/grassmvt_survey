Current survey creation flow
- No create-survey API handler was found in src/worker.js.
- The active survey creation/update path is scripts/seed-surveys-from-jsonc.mjs.
- That script reads survey JSONC files from surveys/, writes SQL, upserts into surveys, then upserts survey_versions.
- Older survey creation also exists in seed migrations db/migrations/0001_survey_tables.sql and db/migrations/0002_seed_more_surveys.sql, but those are historical bootstraps, not the current operational path.

Current Town Hall topic lookup flow
- Survey list UI in public/js/surveys-list.js linked directly to /townhall/topic.html?slug=<survey-slug>.
- Worker-rendered survey pages in src/worker.js also linked directly to /townhall/topic.html?slug=<survey-slug>.
- public/townhall/townhall-topic.js calls /api/townhall/topic/<slug>.
- src/worker.js resolves that route through townhallGetTopicBySlug(), which looks up townhall_topics where slug = ? OR survey_slug = ?.
- If no topic row exists, the API returns TOPIC_NOT_FOUND and the topic page shows "Town Hall not enabled yet".

Exact initialization gap found
- scripts/seed-surveys-from-jsonc.mjs created surveys and survey_versions but did not create townhall_topics.
- Because of that, new surveys could become visible in survey list and survey detail pages before a matching Town Hall topic existed.
- The UI therefore showed active "Discuss topic" links even when the linked Town Hall topic row was missing.

Relationship found before changes
- Current operational relationship was by townhall_topics.survey_slug UNIQUE.
- No explicit survey_id foreign key existed in townhall_topics before this review.

Whether current UI links can be shown before a topic exists
- Yes.
- public/js/surveys-list.js previously rendered "Discuss topic" for every survey card.
- src/worker.js previously rendered "Discuss this topic" for every /surveys/<slug> page.
- Both links were based only on survey slug, not on actual Town Hall topic existence.

Recommended canonical relationship
- Recommendation: townhall_topics.survey_id UNIQUE
- Why this fits the current project better:
  - surveys already has a stable primary key id
  - Town Hall topics are topic-side records with their own title, slug, receipts, moderation, and statements, so the explicit foreign key belongs naturally on townhall_topics
  - public URLs can still use topic slug or survey slug, but the durable database relationship should not depend on a mutable string field
  - this is a smaller schema change than adding surveys.townhall_topic_id and then updating all survey-side writes
- survey_slug is still useful for readable lookup and backward compatibility, but survey_id should be the canonical database link

Remaining risks and follow-ups
- Remote production was not backfilled in this session because that requires live Wrangler remote access and Cloudflare credentials.
- The admin seed-topic endpoint is still a repair path, not the primary survey creation path.
