Survey page logic flow review
- The landing page loads from public/index.html and pulls shared header/footer markup with public/js/include-partials.js. The top action controls are rendered directly in public/index.html, not injected by JavaScript.
- "Take a Survey" and "View Results" on the landing page are anchor links (`<a>`), not `<button>` elements. They link to /surveys/list/ and /surveys/results/?slug=abortion.
- The full-width behavior was caused by the landing-page container in public/css/site.css: `.hero-actions` used `display: flex` with `flex-direction: column`. In a column flex container, child flex items stretch across the cross-axis by default, so the anchor elements appeared as full-width bars even though `.button` itself is `display: inline-block`.
- The survey list page is public/surveys/list/index.html. It loads public/js/surveys-list.js, which checks auth, requests /api/scope/start and /api/auth/me, then loads survey data from /api/surveys/list and public/data/surveys.json. Survey cards render action anchors for starting a survey, viewing results, and discussing the topic.
- The survey results page is public/surveys/results/index.html plus public/js/survey-results.js. Results are filtered client-side by slug from the query string or `/surveys/results/<slug>` path.
- Survey take pages are rendered dynamically by src/worker.js for `/surveys/<slug>` and `/surveys/take/<slug>`. The former serves the SurveyJS app shell; the latter renders the older markdown/template-based take flow and loads public/js/survey-take.js.
- The three lower pills on the landing page were already non-clickable spans in public/index.html. They are decorative/process indicators, not anchors and not wired to section targets. They were not broken controls, but their pill styling could read as clickable chips without any step cue.

Verified district link vs dropdown sync bug
- Root cause
  - The verified district shortcut links and the geography dropdown were using different state update paths inside `public/js/survey-results.js`
  - The verified House link was building keys directly from stored address verification values, which could produce `WY-HD-059`
  - The dropdown options used normalized aggregate keys like `WY-HD-59`
  - Because the shortcut click did not funnel through the same normalization and filter-application path, the page could update badges while leaving the dropdown and results state out of sync
- Old behavior
  - Dropdown change mutated `currentGeoType/currentGeoKey` directly and called `render()`
  - Verified district link click separately forced tier 2, loaded geo options, mutated `currentGeoType/currentGeoKey`, and called `render()`
  - URL load applied only the survey slug, not the same shared filter-selection path
- New unified interaction model
  - All geography selection paths now funnel through one canonical `applyFilter()` function in `public/js/survey-results.js`
  - Covered paths:
    - direct dropdown selection
    - verified district shortcut links
    - URL-based page load
    - tier switching
  - `applyFilter()` now:
    - resolves the target tier and geography
    - normalizes district keys
    - validates against current geo options
    - updates the canonical page state
    - updates the URL query string
    - triggers the same render path for badges, counts, dropdown selection, legislator cards, and low-response notices
