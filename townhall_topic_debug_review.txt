Topic page logic flow
- The page reads the slug from the query string in `/home/anchor/projects/grassmvt_survey/public/townhall/townhall-topic.js`.
- It fetches `/api/townhall/topic/<slug>`.
- The fallback "Town Hall not enabled yet" path is triggered only when one of these is true:
  - response status is `404`
  - payload `ok` is not `true`
  - payload does not include `data.topic`
- If a topic is returned, the page sets the title from `topic.title`, hides the missing panel, and loads statements and receipts.

Exact issue found
- The local data and backend lookup for `abortion` are correct.
- The root cause is a UI-layer CSS bug in `/home/anchor/projects/grassmvt_survey/public/css/site.css`.
- `.is-hidden { display: none; }` was declared before `.card { display: block; }`.
- Both selectors have the same specificity.
- For elements like `<section class="card is-hidden" id="topic-missing">`, the later `.card` rule won and re-displayed the element.
- Result: the page could correctly resolve the topic title while the "Town Hall not enabled yet" card still remained visible.

Classification
- Primary issue: UI bug
- Data issue: not present locally for `abortion`
- API issue: not indicated by the local code path or local D1 row
- Linkage model: `townhall_topics.survey_id` is the durable link, with `survey_slug` and `slug` retained for lookup and compatibility

Root-cause fix
- Make the shared hidden utility win consistently by changing:
  - `.is-hidden { display: none; }`
  - to `.is-hidden { display: none !important; }`

Recommended follow-up
- Keep using the existing topic backfill flow for older surveys if a future survey truly has no `townhall_topics` row.
- If this is also being checked in production, verify the same `abortion` topic row exists remotely before assuming parity with local.

Published statements refresh and tag sync
- Files changed:
  - /home/anchor/projects/grassmvt_survey/public/townhall/townhall-topic.js
- Current publish workflow:
  - `/home/anchor/projects/grassmvt_survey/src/worker.js` currently saves passing Town Hall statements with `status = 'published'`
  - that means a clean statement is expected to become visible in `Published Statements` immediately after a successful post
  - the older `submitted for review` assumption is no longer the default behavior for successful statement posts
- Old bug behavior:
  - initial page load used the fetched published dataset in `state.loadedStatements`
  - post-submit success bypassed that shared dataset and manually prepended a single card into the feed
  - because `state.loadedStatements` was not refreshed, the tag chips, `All` filter, and active tag state could remain stale
  - a newly published statement with a new tag could appear in the feed while the tag browser still omitted that tag
- Canonical refresh path:
  - added `refreshPublishedStatements()` in `/home/anchor/projects/grassmvt_survey/public/townhall/townhall-topic.js`
  - both initial page load and successful publish now use the same flow:
    - fetch the latest published statements
    - replace the full loaded dataset
    - rebuild the available tag chips from that dataset
    - reapply the active tag if it still exists
    - fall back to `All` if the active tag no longer exists
- How tags are rebuilt:
  - chips are generated from `state.loadedStatements`
  - tags are normalized by trimming whitespace, removing leading `#`, and lowercasing
  - displayed labels still show the `#` prefix
- How `All` now works:
  - `All` always renders from the full current `state.loadedStatements` dataset
  - it is no longer dependent on a stale prefiltered subset from the old post-submit shortcut path
- Current user-facing behavior:
  - if the backend returns `pending`, the page still shows:
    - `Your statement was submitted for review. Published statements appear here after review.`
  - if the backend returns `published`, the page now refreshes the published discussion area and shows:
    - `Statement posted. Published statements and tags have been updated.`
