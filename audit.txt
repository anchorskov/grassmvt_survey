1. SYSTEM OVERVIEW
======================================================================

Architecture:
- Cloudflare Worker (src/worker.js, ~8,800 lines) serves as the entire backend
- Static assets served from public/ via Cloudflare ASSETS binding
- D1 database (SQLite-compatible) for persistent storage
- SurveyJS for modern survey rendering (survey-core + survey-js-ui)
- Legacy markdown/template flow coexists alongside SurveyJS
- Auth via Lucia + @noble/hashes (scrypt) + SimpleWebAuthn for passkeys
- Email via Resend (src/server/email/resend.js)
- Town Hall discussion system built into the same Worker

Data Flow (survey definition to user):
  1. JSONC files authored in surveys/
  2. Registered in scripts/seed-surveys-from-jsonc.mjs (surveySources map)
  3. Seeded into D1 via Wrangler d1 execute (surveys + survey_versions + townhall_topics)
  4. Worker serves /api/surveys/<slug> which returns JSON from survey_versions
  5. SurveyJS client (src/surveyjs-app.js, bundled to public/js/surveyjs-bundle.js) renders survey
  6. Responses posted to /api/surveys/<slug>/responses, stored in responses + response_answers
  7. Aggregates updated in response_aggregates and aggregate_rollups
  8. Results served via /api/results/* endpoints, rendered by public/js/survey-results.js

Key Components:
- src/worker.js: All routes, all API handlers, auth, Town Hall, aggregation, rendering
- scripts/seed-surveys-from-jsonc.mjs: Survey seeding pipeline
- public/data/surveys.json: Static metadata catalog (21 entries)
- public/js/survey-browser.js: Shared browse/filter/merge helpers (window.SurveyBrowse)
- public/js/surveys-list.js: Survey list page logic
- public/js/survey-results.js: Results page logic
- public/js/homepage.js: Landing page dynamic behavior
- src/surveyjs-app.js: SurveyJS runtime initialization and submission
- src/lib/townhall-moderation.js: Heuristic-based statement moderation

2. SURVEY DATA MODEL
======================================================================

Where survey data lives:

A) D1 Database (primary):
   - surveys: slug, scope, title, status, flow_type, flow_meta
   - survey_versions: version, json_text, json_hash, published_at
   - responses + response_answers: user responses
   - response_aggregates + aggregate_rollups: pre-computed results

B) JSONC Files (surveys/):
   - 19 active JSONC files, all present and referenced in seed script
   - Source of truth for survey content (SurveyJS JSON)
   - Contains x_meta for flow metadata

C) public/data/surveys.json (static metadata):
   - 21 entries with browse metadata: path, category_slug, display_order,
     estimated_minutes, featured, landing_blurb, status, scope
   - Used as fallback/enrichment by frontend JS

Source of Truth Analysis:
- Survey content (questions/pages): JSONC -> D1 survey_versions (clear chain)
- Survey status: Dual source - D1 surveys.status AND surveys.json status
- Browse metadata (path, category_slug, display_order, estimated_minutes, featured):
  ONLY in surveys.json -- NOT stored in D1 at all
- Title/description: Stored in both D1 and surveys.json; API uses D1  
- D1 surveys.scope is always seeded as 'public' by the seed script, even for
  surveys that are 'wy' in surveys.json

Duplication and Drift Risks:
- CRITICAL: The /api/surveys/list endpoint does NOT return path, category_slug,
  display_order, estimated_minutes, or featured. These fields come ONLY from
  surveys.json via the client-side merge in survey-browser.js.
- If a survey is added to D1 via seeding but not added to surveys.json,
  it will appear in the API list without path or browse metadata. It will
  sort to the end, show no path badge, no estimated minutes, and not be featured.
- surveys.json has 21 entries; seed script has 19 sources. The two extras in
  surveys.json are: "system-responsiveness" (coming_soon, no JSONC) and
  "survey-process" (archived, no JSONC). This is intentional but creates a
  situation where surveys.json contains survey metadata for surveys that may
  not exist in D1.
- The seed script hard-codes scope='public' for ALL surveys. surveys.json has
  scope='wy' for 3 surveys. The client merge uses D1 scope when available,
  so wy-scoped surveys may appear as 'public' in some contexts.

5. SURVEY FLOW
======================================================================

Modern SurveyJS flow:
1. User navigates to /surveys/<slug>
2. Worker renders HTML shell with <div id="surveyjs-root" data-slug="...">
3. surveyjs-bundle.js (built from src/surveyjs-app.js) loads
4. Fetches GET /api/surveys/<slug> -> returns surveyJson, versionId, versionHash
5. Creates SurveyJS Model, checks for existing response via /api/responses/mine
6. If existing response found, prefills answers (editing mode)
7. Handles sectioned flow if x_meta.sectionExitEnabled or x_meta.flow === 'sectioned'
8. On complete, POSTs to /api/surveys/<slug>/responses with answersJson + meta
9. Worker validates session, finds or creates response record
10. Stores answers in response_answers, updates aggregates
11. Shows thank-you modal with receipt ID and campaign promotion

Legacy flow:
1. User navigates to /surveys/take/<slug>
2. Worker renders full HTML form with question_json from survey_questions table
3. Form submits to /api/surveys/<slug>/submit as formData
4. Worker stores submission in survey_submissions + survey_answers
5. Creates/uses survey token for receipt tracking
6. Redirects to next survey or completion page

Validation:
- Modern flow: Requires authenticated session (requireSessionUser)
- Modern flow: Validates versionId exists, optionally validates versionHash
- Modern flow: Validates answers is an object
- Legacy flow: Validates selected_key against hard-coded set (policy_1..policy_5)
- Legacy flow: No authentication required (uses token-based tracking)

Response editing:
- Modern flow: Detects existing response via user_id + survey_version_id
- On edit: increments edit_count, replaces all answer rows, recomputes aggregates
- Unique constraint: idx_responses_user_surveyver_unique prevents duplicates
- Old answers fetched to compute aggregate delta (only adjusts changed choices)

Result storage:
- Raw: responses + response_answers tables
- Aggregated: response_aggregates (question/choice counts per tier/geo)
- Rollups: aggregate_rollups (total response counts per tier/geo)
- Results suppressed below MIN_PUBLISH_N (10 responses)
- Two tiers: Tier 1 (all responses), Tier 2 (verified address)
- Multiple geo contexts: all, state, state_house, state_senate, us_house

6. SEEDING SYSTEM
======================================================================

How JSONC files become DB records (scripts/seed-surveys-from-jsonc.mjs):
1. JSONC file loaded from surveys/ directory
2. Comments stripped via custom stripJsonc parser
3. JSON parsed, x_meta extracted for flow metadata
4. Content canonicalized via stableStringify (sorted keys)
5. SHA-256 hash computed for version identity
6. SQL generated:
   - INSERT OR IGNORE into surveys (creates if new)
   - UPDATE surveys (always updates title, flow_type, flow_meta)
   - INSERT into survey_versions with ON CONFLICT DO UPDATE
   - INSERT OR IGNORE into townhall_topics (creates if new)
   - UPDATE townhall_topics (always updates linked fields)
7. SQL written to temp file, executed via wrangler d1 execute
8. Temp file deleted

Versioning consistency:
- Version number passed via --version CLI arg; same version used for ALL surveys
  in a batch seed (--slug=all). This means all surveys share the same version
  number per seed run, which is correct but requires discipline.
- ON CONFLICT(survey_id, version) handles re-seeding same version
- Hash changes detected by content comparison

Risks of partial or inconsistent seeds:
- Local seeds use BEGIN TRANSACTION; remote/preview seeds do NOT use transactions.
  A failure mid-seed on remote targets will leave partial state.
- Each survey generates a separate SQL INSERT/UPDATE block. If wrangler execution
  fails after some surveys but before others, D1 will have mixed state.
- The seed script generates a random UUID for townhall_topics.id on every run.
  INSERT OR IGNORE prevents duplicates, but the UPDATE always runs and may
  overwrite topic metadata that was customized after initial seed.

Differences between local and remote seeding:
- Local: wraps in BEGIN TRANSACTION / COMMIT
- Remote: no transaction wrapper (Wrangler limitation or deliberate choice)
- Both use the same SQL generation logic
- dbTarget maps: local->wy_local, preview->wy_preview, prod->wy

Seed script scope issue:
- FIXED (2026-03-19): buildSql now accepts a scope parameter instead of
  hardcoding 'public'. Four wy-scoped survey sources (abortion, wy-public-
  school-funding-2026, wy-household-economic-outlook, wy-health-care-costs-
  access-options) now have scope:'wy' in surveySources. The UPDATE statement
  also sets scope, so re-seeding corrects existing D1 rows.
- All four wy surveys re-seeded to production D1 on 2026-03-19.

10. SECURITY & VALIDATION
======================================================================

Input validation:
- parseJsonBody swallows errors -> returns {} on malformed JSON. This means
  most handlers proceed with empty/undefined fields rather than rejecting bad input.
- truncateValue used for string fields in several places (good)
- Email validation via isValidEmail helper
- Slug parameters use decodeURIComponent (some injection risk if not escaped in SQL,
  but parameterized queries via .bind() are used throughout - GOOD)
- escapeHtml used in server-rendered HTML (GOOD)
- Form submissions validated for required fields

API protections:
- Turnstile CAPTCHA enforced for auth routes in production
- Production safety check: refuses to start without TURNSTILE_SECRET_KEY
- enforceTurnstileBypassPolicy prevents TURNSTILE_BYPASS in production
- Origin header checking via requireSameOrigin (POST requests)
- Session-based auth via Lucia for protected endpoints
- Rate limiting on: password reset, email verification, voter verification, Town Hall

Auth assumptions:
- Survey responses require authenticated session (modern flow)
- Legacy /surveys/take/<slug> does NOT require auth (uses token tracking)
- Admin endpoints check: isLocalRequest OR email === 'anchorskov@gmail.com'
  This is a hard-coded admin check. If the admin email changes, code must change.
- Dev endpoints (seed-surveyjs, seed-results, whoami, cookies) guarded by isLocalRequest
  which checks hostname === 'localhost' || '127.0.0.1'. This is appropriate for dev
  but could be bypassed via Host header manipulation in some proxy configurations.
- Passkey step-up verification required for verified voter submissions

Rate limiting concerns:
- localRateLimiters use in-memory Maps. On Cloudflare Workers, each request may
  hit a different isolate. In-memory rate limits are NOT reliable in production.
  Workers can be recycled at any time, resetting all maps.
- D1-backed rate limiting exists for some flows (password reset, email verification)
  which is more reliable but still subject to D1 consistency guarantees.

CORS:
- No explicit CORS preflight (OPTIONS) handling. Access-Control-Expose-Headers is
  set for specific response headers but no Access-Control-Allow-Origin is set.
  This is fine for same-origin deployment but would break any cross-origin API use.

Injection risks:
- SQL: Parameterized queries used consistently via .bind() (GOOD)
- XSS: escapeHtml used in server-rendered content (GOOD)
- An exception: the seed script builds SQL via string concatenation
  (buildSql function), but this runs offline as a CLI tool, not in the Worker.
  The seed script uses single-quote escaping which is the minimum viable defense
  but could theoretically fail on unusual characters in survey JSON content.

Admin backfill endpoint:
- FIXED (2026-03-19): /api/admin/backfill-aggregates auth check now correctly
  uses sessionResult.status === 'valid' and sessionResult.user.email instead
  of the broken pattern that treated the wrapper object as the user. Previously,
  remote requests were always rejected (safe failure) because the wrapper
  object's .email was undefined. Now the guard works as intended.

11. PERFORMANCE & SCALING
======================================================================

Potential bottlenecks:

1. /api/surveys/list executes a complex JOIN across surveys, survey_versions,
   townhall_topics, and responses. The subquery for latest published version
   runs for every survey row. With many surveys, this could slow down.

2. Response submission writes to responses, then loops through all answer entries
   writing response_answers one at a time. For surveys with many questions (e.g., 30+),
   this generates 30+ individual DB writes per submission. Could benefit from batching.

3. Aggregate updates on submission loop through all geoContexts (up to ~5) and
   all changed answers, each generating a separate DB operation. This compounds
   with the per-answer writes above.

4. /api/admin/backfill-aggregates processes ALL responses in a single request.
   For any significant number of responses, this will hit Worker execution time
   limits (Workers have a 30-second limit on free plan, 5-minute on paid).

5. Worker.js is a single ~8,800-line file. While this doesn't affect runtime
   performance, it impacts maintainability and makes it harder to identify
   performance issues or refactor hot paths.

Redundant queries:
- Both survey-results.js and surveys-list.js fetch /api/surveys/list independently.
  The results page also fetches surveys.json separately. On the results page, both
  data sources are loaded to populate the survey selector.
- homepage.js fetches /api/auth/me twice: once via AuthUI.fetchAuthState() and
  once directly via fetch('/api/auth/me').
- The /api/surveys/list endpoint parses json_text for every survey to extract
  description, even though description could be stored as a column.

Client-side vs server-side filtering:
- ALL survey path filtering happens client-side. The API returns all published
  surveys regardless of path. For a small catalog (19-21 surveys) this is fine,
  but at scale (100+ surveys), returning all surveys for every browse page view
  would be wasteful.
- Results geo filtering is properly server-side via aggregate queries.

   from HIGH to LOW. The in-memory fallback is unreliable across isolates,
   but the D1-backed path is the production default.

4. DUPLICATE MIGRATION NUMBER 0015 (ACCEPTED -- cannot safely rename)
   Files: db/migrations/0015_add_district_to_user_address_verification.sql,
          db/migrations/0015_add_senate_district.sql
   Two files share migration number 0015. One is a no-op marker, the other

   not by number prefix, so both are tracked independently and both have
   already been applied in local and production. Renaming would cause Wrangler
   to see the renamed file as a new unapplied migration, which would fail.
   Risk is cosmetic only; no action needed.

   File: src/worker.js (multiple locations, e.g., backfill-aggregates)

   File: scripts/seed-surveys-from-jsonc.mjs, main function

7. ADMIN BACKFILL ENDPOINT AUTH CHECK -- FIXED (2026-03-19)
   File: src/worker.js (~line 8732)
   Was: getSessionUser returns {status, user} but code treated wrapper as user.

   wrapper.email was undefined (safe failure mode, but wrong reason).
   Fix: Now checks sessionResult.status === 'valid' && sessionResult.user.email.

8. parseJsonBody ERROR HANDLING -- FIXED (2026-03-19)
   File: src/worker.js (line 219)
   Was: Returned silent {} on any JSON parse failure.
   Fix: Now logs console.warn with the error message and returns {_parseError:true}.
   All 30+ existing callers continue to work unchanged (they destructure specific

   Deployed to production: 2026-03-19.

9. LEGACY FLOW COEXISTS WITHOUT SHARED AUTH
   Files: /surveys/take/<slug> routes, survey-take.js
   The legacy flow uses token-based tracking without proper user authentication.
   Responses from this flow are stored in different tables (survey_submissions/
   survey_answers) than the modern flow (responses/response_answers). The two
   systems share no response linkage or aggregate integration.

10. stripJsonc DUPLICATED IN FOUR FILES
    Files: survey-browser.js, survey-results.js, surveys-render.js,
           scripts/seed-surveys-from-jsonc.mjs
    A bug in any copy could produce different parsing behavior across
    client and server, leading to hard-to-diagnose data issues.

11. surveys-render.js READS ONLY FROM surveys.json
    File: public/js/surveys-render.js
    This file completely ignores the API and D1 data. If it is still used
    anywhere, it shows stale or inconsistent survey listings.

12. WORKER FILE SIZE
    File: src/worker.js (~8,800 lines)
    Extremely large single-file Worker containing auth, survey, Town Hall,
    aggregation, admin, location, and rendering logic. High cognitive load
    for maintenance and high risk of unintended side effects.

13. NO HEAD REQUEST HANDLING
    File: src/worker.js
    No explicit HEAD request support. Monitoring tools, CDNs, or health checks
    using HEAD requests will either hit the static asset handler or get 404.

14. HOMEPAGE FETCHES AUTH TWICE
    File: public/js/homepage.js
    Calls AuthUI.fetchAuthState() and then separately fetches /api/auth/me.
    Doubles the auth request load on every homepage visit for logged-in users.
